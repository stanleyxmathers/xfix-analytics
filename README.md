# XFIX Service Center Analytics

Аналитика целевых действий сервисного центра (Apple / Яндекс) на Supabase.
Дашборд — один статичный HTML-файл, вся логика в PostgreSQL-функциях.

## Структура проекта

```
├── dashboard.html            # весь фронтенд (открыть в браузере)
├── proxy.py                  # локальный статик-сервер для разработки
├── supabase_schema.sql       # таблицы, индексы, RLS
├── supabase_functions.sql    # RPC поверх report_id (импорт + чтение)
├── supabase_periods.sql      # слой периодов: неделя / месяц / квартал / диапазон
├── supabase_health.sql       # журнал ошибок + снимок состояния Postgres
├── supabase_issue_checks.sql # проверки перед выдачей
├── supabase_kpi.sql          # KPI руководителя: схемы по месяцам, история до окт. 2026
├── supabase_unified_upload.sql # один отчёт на всё: импорт, KPI из actions, «мой отдел»
└── supabase/functions/db-health/index.ts   # Edge Function: прокси к Metrics API
```

## Архитектура

```
Excel (.xlsx) ──parse в браузере (SheetJS)──> import_report_rows()
                                                    │
                                         Supabase PostgreSQL
                                                    │
dashboard.html <──supabase-js RPC──────────────────┘
```

Бэкенда как отдельного сервиса нет. Браузер разбирает Excel сам, шлёт строки
пачками в RPC, дальше всё считает база. Роль `anon` не имеет прав на таблицы —
только вызов функций (`SECURITY DEFINER`).

## Первичная настройка

### 1. Создать проект Supabase

[supabase.com](https://supabase.com) → New project. Понадобятся **Project URL**
и **anon key** (Settings → API).

### 2. Прогнать SQL в Supabase SQL Editor — строго в этом порядке

```
1. supabase_schema.sql      # таблицы
2. supabase_functions.sql   # RPC поверх report_id
3. supabase_periods.sql     # слой периодов (зависит от п.2)
4. supabase_health.sql      # мониторинг (можно позже)
5. supabase_issue_checks.sql, supabase_kpi.sql, supabase_duty.sql, supabase_schedule.sql
6. supabase_unified_upload.sql  # импорт общего отчёта (зависит от п.2 и п.5)
```

Грузится один общий отчёт (все сотрудники, все типы действий, колонки «Маркер корп»,
«Ключ просрочен», «id»). Из него собираются недели и перерасход, еженедельный отчёт,
KPI руководителя за месяц и проверки перед выдачей.

Показатели дашборда (Главная, перерасход, сотрудники, еженедельный отчёт, аномалии)
считаются только по «моему отделу» (Настройки → Сотрудники → Мой отдел): функции читают
представление `dept_actions` вместо `actions`. KPI руководителя и проверки — по всем действиям.

### 3. Указать ключи в дашборде

Открыть `dashboard.html` → **Настройки → Подключение** → вставить Project URL
и anon key. Сохраняются в `localStorage` браузера, в файл не пишутся.

### 4. Локальный запуск (опционально)

```bash
python3 proxy.py     # http://localhost:8080/dashboard.html
```

Файл можно открыть и напрямую (`file://`) — Supabase отдаёт CORS, прокси не нужен.

## Загрузка отчёта

1. Экспортировать Excel из внутренней системы за нужную неделю
2. Дашборд → **Загрузить отчёт** → перетащить файл
3. Браузер разбирает файл, при необходимости режет на несколько недель
   (`splitRowsByWeek`) и грузит каждую как отдельный отчёт

Что происходит на стороне БД:

| Шаг | Функция | Что делает |
|---|---|---|
| 1 | `import_report_rows` | пишет `uploads` + `actions` пачками |
| 2 | `import_report_recompute` | сворачивает действия в `services`, считает зоны и перерасход |
| 3 | `import_report_stats` | `employee_stats`, `anomalies`, `weekly_insights` |
| 4 | `import_analyze` | `ANALYZE` по затронутым таблицам |

Если шаг падает — отчёт откатывается через `delete_report`, полузагруженных
недель не остаётся.

## Формат входного Excel

Одна строка = одно действие мастера.

| Колонка | Поле | Описание |
|---------|------|----------|
| A | id | ID действия |
| B | ФИО | Имя сотрудника |
| C | дата | Дата действия (Excel serial или дата) |
| E | Офис | Офис |
| F | Отдел | Отдел |
| G | Тип | Тип действия |
| H | Группа | Группа/устройство |
| I | Подгруппа | Подгруппа |
| J | Комментарий | Комментарий |
| K | price | Стоимость, ₽ |
| X | id сервис | ID обращения (несколько строк на одно обращение) |
| AK | Вендор | Apple / Яндекс |

> Заголовки распознаются автоматически: и буквенные (A, B, C…), и русские.

| `period_employee_stats` | статистика сотрудников за период |

## Периоды

Дашборд изначально работал на одном `report_id` — снимке недели. Проблема:
обращение, растянутое на две недели, попадало в оба отчёта, базовая стоимость
задваивалась, зоны врали.

Слой периодов пересчитывает обращения по `service_id` **сквозь** выбранные
недели. Селектор в шапке: **Неделя / Месяц / Квартал / Произвольно**, рядом —
выбор базы для сравнения.

Сборка периода: `period_begin` → `period_build_services` → `period_build_stats`
→ `period_finish`. Разбита на чанки, т.к. платформа режет `statement_timeout`
на 3 секунды; фронт (`buildInChunks`) докручивает сборку и показывает прогресс.

Результат кэшируется. Период пересобирается, если изменились `action_settings`
(сверяется `settings_stamp`) или добавились отчёты.

Все read-функции имеют две версии: `get_*` (по `report_id`) и `get_*_p`
(по ключу периода) — например `get_overview` / `get_overview_p`.

## Логика аналитики

### Зоны обращений
| Зона | Условие | Маркировка |
|---|---|---|
| Норма | стоимость ≤ базовой | ✓ |
| Повышен | стоимость > базовой × 1.3 | 🟡 |
| Критично | стоимость > базовой × 2 | 🔴 |

### Базовая стоимость обращения
Считается по разметке в `action_settings`: действия с `is_base = true` образуют
базовый набор для комбинации вендор + группа. Разметка правится вручную в
**Настройки → Действия** (в т.ч. импортом из Excel), после правки затронутые
периоды пересобираются.

### Аномалии сотрудников
- средняя стоимость обращения **> 120%** от средней по отделу → предупреждение
- средняя стоимость обращения **> 150%** → критично
- общий перерасход **> 130%** от среднего по отделу → предупреждение
- общий перерасход **> 200%** → критично

Отдел берётся из данных или из ручной привязки `employee_departments`.

### Разбор дублей

Дубль = одно и то же действие (`employee` + `service_id` + `action_type`) проведено
больше одного раза. Часть таких случаев дублями не является: несколько одинаковых
услуг на обращении или разные работы, которые пишутся одним названием действия.

На странице «Отдел диагностики» каждый дубль можно пометить:

| Пометка | Что значит |
|---|---|
| **удалён** (`resolved`) | дубль реальный, лишние строки удалены в учётной базе |
| **не дубль** (`not_duplicate`) | по факту не дубль (несколько услуг / разные работы) |

Помеченный случай уходит из счётчика «Всего дублирований», из колонки дублей
в таблице сотрудников и из ленты аномалий. Пометка привязана к числу повторов
на момент разбора (`reviewed_repeat_count`): если после переимпорта повторов
стало больше, случай снова появится в статистике. Кнопка «вернуть» снимает пометку,
чекбокс «Показывать разобранные» в drill-down показывает уже разобранные случаи.

### Инсайты
Генерируются при изменении показателя **> 5%** к базе сравнения: количество
обращений, сумма выплат, перерасход, средняя стоимость. Нужны минимум два
периода — с первой загрузки инсайтов не будет.

## Мониторинг состояния БД

Раздел **Настройки → Состояние БД**. Два независимых источника, второй опционален.

### Слой 2 — журнал ошибок и снимок Postgres (обязательный)

Прогнать `supabase_health.sql` в Supabase SQL Editor. Создаёт:

| Объект | Назначение |
|---|---|
| `app_error_log` | журнал ошибок запросов, ретеншн 30 дней |
| `log_client_error()` | единственный путь записи для `anon` (SECURITY DEFINER) |
| `get_error_log()` / `get_error_summary()` | чтение журнала |
| `db_health_snapshot()` | коннекты, откаты транзакций, cache hit, deadlocks, размеры таблиц |
| `db_slow_queries()` | топ по `pg_stat_statements` (если расширение включено) |

Дашборд пишет в журнал автоматически: `instrumentSupabase()` подменяет `sb.rpc`/`sb.from`,
любая неудача запроса уезжает в `app_error_log` без правок в вызывающем коде.
Таймауты, которые успешно переигрывает `rpcWithRetry`, не логируются — только исчерпанный ретрай.

Прямого доступа к `app_error_log` у `anon` нет: RLS включён, политик нет, права отозваны.

### Слой 1 — Supabase Metrics API (опциональный)

Metrics API (`/customer/v1/privileged/metrics`) требует HTTP Basic с **service_role key**
и не отдаёт CORS — из браузера недоступен. Ключ такого уровня в статичном дашборде
держать нельзя, поэтому запрос идёт через Edge Function, где ключ лежит в секретах проекта.

```bash
supabase secrets set XFIX_METRICS_KEY=<service_role key>
supabase functions deploy db-health
```

Функция тянет Prometheus-текст, отбирает ~20 метрик (`pg_up`, диск, память, CPU,
пул соединений, deadlocks) и отдаёт JSON. Скорости (транзакций/с, откатов/с, CPU %)
дашборд считает как дельту между опросами — счётчики Prometheus монотонные.

Без деплоя функции блок «Инфраструктура» показывает подсказку, остальное работает.

## Устранение проблем

**Дашборд не грузит данные**
Проверить URL и anon key в **Настройки → Подключение**, затем **Настройки →
Состояние БД → журнал ошибок** — туда пишутся все упавшие запросы с текстом ошибки.

**Запрос падает по таймауту**
Платформа режет `statement_timeout` на 3s. `rpcWithRetry` переигрывает такие
запросы сам; если ретраи исчерпаны — запись появится в журнале ошибок.
Тяжёлые периоды собираются чанками, при зависании — пересобрать период
(смена периода в шапке и обратно).

**Сборка периода не заканчивается**
Смотреть `periods.built_at` — `NULL` означает «не собран». Строку периода можно
удалить, сборка начнётся заново.

**Зоны и перерасход выглядят неверно**
Проверить разметку в **Настройки → Действия**: если базовый набор для группы
не размечен, база считается по неполному набору.

**Нет инсайтов**
Нужен предыдущий период для сравнения — с первой загрузки их не будет.
Порог: изменение > 5%, задан в SQL.
