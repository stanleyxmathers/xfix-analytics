# Приоритизация задач объединённого отдела (диагностика + логистика) — спецификация

Черновик, собирается по итогам обсуждения 29.10.2026. Расширяет раздел «Планирование»
(`Планирование_спецификация.md`, `supabase_planning.sql`): тот же метод норм и ёмкости,
но на обе функции отдела и с расчётом внутри смены.

## Что решено

- **Источник очереди** — FileMaker. Статусами управляют скрипты FM.
- **Обмен** — FileMaker Data API (REST), скрипт по расписанию на сервере fivenine
  пишет снимок в Supabase. Claris MCP — только для разведки схемы и разовых запросов,
  не для регулярной синхронизации (см. «Почему не MCP»).
- **Нормы логистики** считаются тем же методом интервалов между действиями, что и у
  диагностики: у действий есть только время выполнения, длительность — интервал от
  предыдущего действия сотрудника, интервалы больше 40 мин — простой. Действия логистики
  в выгрузке — `Отдел = Логистика`.
- **Отделы** объединяются в `employee_departments`; правило «помощь со стороны» убирается.
- **Сроки:**
  - срок в статусе — поле FM, своё для каждого типа техники и статуса (внутренние метрики + поправка на вендора);
  - клиентский срок — 45 дней на выполнение работ, дальше возврат средств; сроки в статусах его в основном уже учитывают;
  - маркер «Экспресс» — выдавать оперативно;
  - отправка готовой техники клиентам — вторник и пятница, готово к 15:00 МСК; оплата приходит, когда клиент получил устройство;
  - командировка в АСЦ — период, направление, кто едет, список техники; добавить можно за час до отъезда, лучше раньше.
- **Деньги напрямую не взвешиваются.** Выручки за минуту нет, цена согласованных работ —
  не опора. Деньги учитываются через отправки клиентам: устройство, не успевшее к 15:00
  вторника, уходит в пятницу (+3 дня до оплаты), не успевшее в пятницу — во вторник (+4 дня).
- **Стажёры** (2 человека) — допуски к типам задач правятся вручную, система учитывает их в распределении.

## Правило приоритета (предложение)

1. **Экспресс** — первым.
2. **Жёсткие сроки по запасу времени**, где запас = срок − сейчас − оставшаяся работа по нормам:
   - срок в статусе (FM);
   - командировка: отъезд − буфер (по умолчанию накануне вечером, минимум − 1 ч);
   - отправка клиентам: ближайшие вт/пт 15:00 для готовой техники, которая едет ТК
     (выходная диагностика → проверка → упаковка);
   - клиентский срок 45 дней.
3. **Остальное** — по ближайшему сроку в статусе, при равенстве — по дате приёма.

## Поля для выгрузки из FileMaker

Имена в первом столбце — как будут называться колонки в Supabase. Если в FM поле
называется иначе — пришлите соответствие, маппинг будет в скрипте.

### 1. Устройство (заказ) — одна строка на устройство в работе

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `service_id` | число | да | id сервиса — тот же, что колонка «id сервис» в выгрузке действий. Ключ связи с нормами |
| `order_no` | текст | | номер заказа, если отличается от `service_id` |
| `vendor` | текст | да | Apple / Яндекс |
| `device_group` | текст | да | группа техники, как «Группа» в выгрузке действий (iPhone, AirPods…) |
| `device_name` | текст | | наименование / модель |
| `status` | текст | да | текущий статус, как в FM |
| `status_since` | дата-время | да | когда устройство вошло в текущий статус |
| `status_deadline` | дата-время | да | когда истекает срок в статусе (абсолютное время, не остаток) |
| `accepted_at` | дата-время | да | дата и время приёма |
| `client_deadline` | дата | да | окончание 45-дневного срока |
| `is_express` | да/нет | да | маркер «Экспресс» |
| `intake_method` | текст | | ТК / клиент сам — для статусов «Доставка» и «Ожидаем получения» |
| `expected_arrival` | дата | | ожидаемая дата поступления (для «Доставка») |
| `intake_waybill` | текст | | накладная ТК на поступление |
| `return_method` | текст | да | как отдаём клиенту: самовывоз / ТК — нужно для отправок вт/пт |
| `trip_id` | текст | | командировка, в которую помещено устройство |
| `assignee` | текст | | кто сейчас ведёт устройство, если назначен |
| `is_paid_repair` | да/нет | | платный ремонт (через согласование) или гарантия |
| `modified_at` | дата-время | да | время последнего изменения записи — для инкрементальной выгрузки |

### 2. Командировка — одна строка на командировку

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `trip_id` | текст | да | ключ |
| `date_from`, `date_to` | дата | да | период |
| `departure_at` | дата-время | да | время отъезда — от него считается срок готовности партии. Если поля нет в FM — нужно завести или договориться о стандартном часе |
| `destination` | текст | да | направление / АСЦ |
| `travelers` | текст | | кто едет (через запятую) — эти люди выпадают из ёмкости смены |
| `trip_status` | текст | | план / собрана / уехала / вернулась |
| `modified_at` | дата-время | да | для инкрементальной выгрузки |

Состав командировки — через `trip_id` в карточке устройства (таблица 1). Если в FM это
отдельная связующая таблица — выгрузить её: `trip_id`, `service_id`, `added_at`.

### 3. История статусов (желательно)

| Поле | Тип | Описание |
|---|---|---|
| `service_id` | число | устройство |
| `status` | текст | статус |
| `entered_at` | дата-время | вход в статус |
| `left_at` | дата-время | выход (пусто — текущий) |
| `changed_by` | текст | кто перевёл |

Нужна для: длительности этапов, сверки «план vs факт», прогноза, когда устройство
дойдёт до следующего этапа.

### 4. Справочник сроков в статусе

| Поле | Тип | Описание |
|---|---|---|
| `device_group` | текст | тип техники |
| `vendor` | текст | вендор (или пусто — для всех) |
| `status` | текст | статус |
| `hours` | число | срок в статусе, часов |

Нужен, чтобы предсказать срок следующего статуса до того, как FM его выставит
(например, срок «На отправку» после диагностики).

## Почему Data API, а не MCP

- MCP — интерфейс для AI-ассистента: разовые запросы в диалоге. Для синхронизации
  по расписанию без участия человека он не предназначен.
- Официальный Claris MCP требует FileMaker Server 22.0.2+ с включёнными Data API и OData,
  то есть Data API всё равно нужен.
- Data API отдаёт ровно поля выбранного макета: под выгрузку заводится отдельный
  макет с полями из таблиц выше, без контейнеров.
- Учётка для скрипта — только чтение, только этот макет. Токен хранится на сервере
  fivenine, в браузер и репозиторий не попадает.

MCP полезен на этапе разведки: посмотреть таблицы, поля, значения статусов.

## Открытые вопросы

- Статусы после «На отправку» и других веток (АСЦ → возврат → выходная → готово → выдано),
  кто выполняет шаг в каждом статусе, какие статусы — ожидание (задачи для отдела нет).
- «На осмотр внутри», «К заказу», «Определение стратегии» — работа нашего отдела или других?
- Время отъезда командировки — есть в FM или только даты?
- Экспресс — какой срок выдачи?
- Не дёргать сотрудников: блоки ролей, лимит переключений (предложение — блок ≥ 2 ч, ≤ 2 перестановок за смену).
- Где смотрит план: старший смены в дашборде / личный список у сотрудника.
- ₽/час по типам задач — посчитать, когда будут нормы логистики.
